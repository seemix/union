Дата замірів: 2026-11-21. Lighthouse 13.6.0, мобільний профіль за замовчуванням (Slow 4G, CPU ×4), 3 прогони на URL, береться **медіанний** за Performance.

## Як міряли (і чого це не доводить)

- **Прод** — реальні `https://ru|ro.baptist.org.md`.
- **v2** — локальна `next build && next start` з **реальним WP** (без моків), перед нею локальний TLS-проксі (`scripts/tls-proxy.mjs`, самопідписаний сертифікат): CSP має `upgrade-insecure-requests`, тому по http підресурси не вантажаться. Chrome мапить `ru|ro.baptist.org.md` на цей проксі, тож Host — прод-овий (немає staging-`noindex`, правильний canonical).
- Це **не staging**: немає CDN/HTTP2/реального хостингу cPanel. При симульованому тротлінгу мережа до сервера майже не впливає, але TTFB на хостингу треба перевірити повторно на `next.*` (`npm run perf` після зміни URL або на staging, див. нижче).
- Розкид між прогонами великий (напр. прод ro home: 58/90/86; v2 ro post: 92/61/90), тому одиничним числам вірити не варто, лише порядку величин.
- Відтворити: `npx next build && npx next start -p 3200`, `node scripts/tls-proxy.mjs`, `node scripts/lighthouse.mjs` (`LH_ONLY=v2|prod`, `LH_RUNS`). Сертифікат — команда в шапці `scripts/tls-proxy.mjs`. Деталі одного URL (фази LCP): `node scripts/lh-detail.mjs <url> [v2]`. Сирі результати: `perf/lighthouse*.json`.

## Результат

- **SEO**: v2 = 100 скрізь (прод 91 на головній/категоріях) — ціль виконана.
- **Best Practices**: ≥ 90 скрізь; ro: 92–96 через `errors-in-console`/`inspector-issues` (див. нижче).
- **Accessibility**: ≥ 90 скрізь (90–96), але є непройдені аудити.
- **Performance**: **ціль ≥ 90 досягнута лише на ro-пості (90, на межі)**; v2 за Performance **гірший за прод на всіх шести сторінках** (головна −4…−11, категорії −13…−31, пости −3…−8). Найгірше — категорії (TBT, CLS, вага) та LCP на головній/категоріях; на ro-пості LCP кращий за прод, але TBT 403 мс. Тому пункт ROADMAP «Lighthouse ≥ 90» **не закрито**.

## Що не дотягує: причини і виправлення

### Performance

| Причина | Докази | Виправлення | Стан |
|---|---|---|---|
| Уся сторінка в SSR мала `style="opacity:0"` (page transition у `template.tsx`) → невидима до гідратації | у HTML `opacity:0`; LCP ≈ 5 с на всіх сторінках | Перша (серверна) сторінка без анімації, fade лише для клієнтських переходів (`src/app/[site]/template.tsx`) | **зроблено**; ефект у межах шуму (ru home 77 → 80, ru post 80 → 81). Це виправлення правильне саме по собі (контент не має ховатись до JS), але не головна причина |
| LCP-елемент на головній — `<img>` слайдера, створений Swiper-ом після гідратації (static-слайд підміняється клієнтським), + важкий JS на старті (bootup ≈ 1.4 с, main-thread ≈ 2.7 с, ~60 KiB невикористаного JS) | `lcp-breakdown`: element render delay; спроба поставити `priority` першим слайдам малих слайдерів LCP не змінила (відкочено) | Рендерити перший слайд так, щоб його `<img>` не замінювався (Swiper ініціалізувати на тому ж DOM або віддавати слайдер статикою до взаємодії); динамічно підвантажувати Swiper/`motion` (`next/dynamic`, init після `requestIdleCallback`); `Reveal` не обгортати карти над згином | відкрито |
| TBT 170–400 мс | JS-гідратація, Swiper, `motion` | те саме + розділити client-компоненти; прибрати `motion` з `Reveal` на користь CSS (`animation-timeline`/IntersectionObserver) | відкрито |
| CLS 0.352 на ru category | у цьому прогоні; в інших 0.000 → нестабільно | Перевірити різновисотні картки/зображення без `width/height`, шрифт `swap`; повторити замір | відкрито, потребує перевірки |
| Вага: ro post 1.6 МБ | картинки в контенті поста WP | `next/image` для зображень контенту (зараз `ContentRender`), `sizes` | відкрито |

### Accessibility (оцінка ≥ 90, але аудити не пройдені)

- `color-contrast` — усі сторінки (червоні/зелені мітки `Label`, світлі підписи на фото): підняти контраст кольорів до 4.5:1.
- `heading-order` — на головній/постах (`h1` → `h3` у картках без `h2`): сабхедінги карток зробити `h2` або відкорегувати ієрархію.
- `link-name`, `presentation-role-conflict` — ru post (контент WP, ймовірно, посилання-картинки без alt та `role="presentation"` на фокусованих елементах): виправляти в `sanitize.ts`/`ContentRender` (підставляти `aria-label`).

### Best Practices (ro 92–96)

- `errors-in-console` / `inspector-issues` на ro (пост, головна): ймовірно, ресурси з контенту, заблоковані CSP (`img-src` лише `self` + baptist.org.md) або 404 зображень. **Причину не встановлено**: відкрити в DevTools консоль ro-поста і зафіксувати URL.

## Не зроблено / обмеження

- Заміри не на staging (його ще немає, ROADMAP етап 9): повторити `LH_*` після розгортання `next.*` і порівняти TTFB/HTTP2.
- Core Web Vitals польові (CrUX) не знімались, лише лабораторні.
- Прод міряли 3 прогони; ru/ro прод теж не ≥ 90 за Performance на головній (84/86), тому «не гірше за прод» — реалістична мінімальна ціль, поки не знято JS-вартість.
